---
title: 为 Java 微服务配置 Dynatrace APM
date: 2024-11-15
---

给 Java 微服务上监控，最省事的办法是让 Dynatrace 的 OneAgent 自动发现。装好 Agent 之后不用改代码，服务、调用链、JVM 指标基本都能直接看到。这篇记录从安装到告警的完整做法。

## 安装 OneAgent

Dynatrace 分两种部署：SaaS 和 Managed。自建环境一般用 Managed，云上直接用 SaaS。拿到环境之后，在 Dynatrace 界面部署 OneAgent，按提示在主机上执行安装命令。

Java 应用不需要改启动参数，OneAgent 会自动识别 JVM 进程并注入探针。装完之后等几分钟，界面上就能看到主机和上面的 Java 进程。如果没出现，先检查这三点：

- 主机和 Dynatrace 环境之间的网络是不是通的，443 端口有没有放行。
- OneAgent 服务是不是在运行，`systemctl status oneagent` 看一下。
- Java 进程是不是 OneAgent 支持的版本，太老的 JVM 需要手动确认。

## 自动发现能看到什么

OneAgent 起来之后，Dynatrace 会自动画出服务拓扑：

- **服务**：每个 Java 微服务、数据库、消息队列都会被识别出来，调用关系自动连线。
- **PurePath**：每次请求的完整调用链，从入口到数据库查询都能展开看，慢在哪一步一目了然。
- **JVM 指标**：堆内存、GC 次数和耗时、线程数、类加载数，不用再单独配 JMX。

这些都不用写配置，开箱就有。想看某个接口的慢请求，直接点进服务，看响应时间分布和最慢的几条 PurePath。

## 自定义仪表盘

默认的视图够用，但每个团队关心的东西不一样，值得建一块自己的仪表盘。常用的几块：

- **关键服务响应时间**：P50、P90、P99 三条线放一起，发布之后一眼看出有没有变慢。
- **错误率**：按服务分组，超过 1% 就标红。
- **JVM 健康**：堆内存使用率、GC 耗时、线程池排队情况。
- **基础设施**：CPU、内存、磁盘 IO，出了问题先排除是不是机器的问题。

仪表盘可以按环境分开，比如生产和预发布各一块，避免看错环境。

## SLA 告警

监控的目的是出问题时能第一时间知道，而不是事后翻日志。建议至少配这几条告警：

- **可用性**：服务 5 分钟内错误率超过 5%，发告警。
- **响应时间**：P90 超过平时基线的两倍，持续 5 分钟，发告警。
- **JVM**：堆内存使用率超过 85%，或者 Full GC 频繁，发告警。
- **主机**：CPU 持续超过 90%，或者磁盘剩余空间小于 10%，发告警。

Dynatrace 的告警自带基线学习功能，它会根据过去几周的数据自动判断什么是“正常”，减少误报。刚开始可以先用默认阈值跑两周，再根据误报情况慢慢收紧。

## 几个容易踩的坑

- **采样率**：高并发服务默认采样可能丢掉一些慢请求，关键接口可以把采样调高一点。
- **自定义指标**：业务指标（比如订单量、支付成功率）OneAgent 看不到，需要用 API 或者 SDK 自己埋点。
- **版本升级**：OneAgent 会自动升级，大版本升级前先在预发布环境验证，避免探针和新版 JVM 不兼容。
- **权限**：OneAgent 需要 root 或者对应权限安装，容器环境要确认镜像里有没有留出安装位置。

配好之后，日常排障的流程就变成：收到告警 → 看仪表盘定位到服务 → 点 PurePath 看慢在哪一步 → 再看代码或者配置。大部分问题在 Dynatrace 里就能定位到根因，不用再到处翻日志。
